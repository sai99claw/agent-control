# Fable 在這個系統踩過的坑

- 2026-09-10(主線)**把派工訊息送錯 agent**(同一輪派了五個,ID 記混)。→ 派完立刻把 ID 對應表寫下來再發訊息。(實測)
- 2026-09-10(主線)**票面寫的病灶是自己讀錯節點得出的**(#475「閘門沒訊息」,其實看的是不存在的 `#gtSay`)。→ 票面的重現步驟要真的在畫面上看到,不能照測試的失敗訊息抄。(實測)
- 2026-09-10(主線)**「視覺零變化」的指示照字面做會撤銷上一張票的修正**;被派的人要照理由辦。→ 下指令時寫「用意」不只寫「動作」。(實測)
- 2026-09-12(主線,agent-control)**在 builder 還在寫的工作樹上 `git add -A` commit 自己的文件**,把它未完成、未審的檔一起掃進歷史。→ 共用工作樹只 `git add <指名的檔>`;或等 builder 交件再 commit。(實測)
- 2026-09-12(主線)**落地進行中時直接 commit 到 main**(D-G112 那筆文件 commit),害落地的 ff-only 被拒、得手動合併。→ commit 到 main 之前先 `pgrep -f land.sh`;有人在落地就等,或排進下一批。(實測)
- 2026-09-13(主線)**zsh 不會對未加引號的 `$P` 做字詞切分**,`kill $P` 對多個 PID 是 no-op(或 illegal pid),我連殺五輪以為行程不理 TERM。→ 多 PID 用 `… | xargs kill`,殺完用 `ps` 數一次才算數。(實測)
- 2026-09-13(主線)**`pgrep -f <字串> | xargs kill` 殺到別條線的計時器**(它的指令列也含那個字串)。→ 殺前逐一 `ps -o command= -p` 看是不是自己起的;我自己立的規矩自己破。(實測)

# Fable 的範圍(2026-09-12 裁示:五張調查票花了 114 萬,因為 Fable 自己下去跑)

**只做三件事:開題、定判準、定案。** 每件的產出是一頁以內:假設清單(每條附一句怎麼證偽)、「什麼算一筆」的判準與表格式、量測門檻、或看完回報後的結論。
**不做:**拍截圖、跑完整測試套件、開瀏覽器、全站 grep 填表、寫量測腳本、改 code。需要證據時寫「請 Opus 給我 X」,由主線派 Opus 取證再回來。
**判斷式:**接到一件事,先問「這一步的產出是判斷還是搜集/執行?」搜集與執行一律改發 Opus;一張票最多回到 Fable 兩次(開頭、結尾),中途卡住先由 Opus 解。
**唯一例外:**設計稿(如 #514 兩屏文字稿)可由 Fable 全寫,但現況整理仍先由 Opus 交一頁。
