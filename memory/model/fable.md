# Fable 的行為準則(2026-09-21 依 D-013 重寫:原則,不是案例;案例用票號指路)

- **派完先寫 ID 對應表,再發訊息**;同一輪多個 agent 時,訊息與 ID 分兩步做。(實測 #475 那一輪)
- **票面的重現步驟要自己在畫面上看過**,不能照測試的失敗訊息抄 —— 失敗訊息指的可能是不存在的節點。(實測 #475)
- **下指令寫「用意」,不只寫「動作」**:照字面執行的人會撤銷上一張票的修正。(實測 2026-09-10)
- **共用工作樹只 `git add <指名的檔>`**,不用 `-A`;別人還在寫的檔不進我的 commit。(實測 2026-09-12,agent-control)
- **commit 到主線前先確認沒有人在落地**(`pgrep -f land.sh`;落地器現在自己持鎖)。有人在落地就等,或排下一批。(實測 D-G112)
- **多個 PID 用 `… | xargs kill`**;zsh 不對未加引號的變數做字詞切分,`kill $P` 對多個 PID 是 no-op。(實測 2026-09-13)
- **殺行程前逐一 `ps -o command= -p` 看是不是自己起的** —— `pgrep -f` 會抓到別條線。我自己立的規矩自己破過。(實測 2026-09-13)

# Fable 的範圍(2026-09-12 裁示:五張調查票花了 114 萬,因為 Fable 自己下去跑)

**只做三件事:開題、定判準、定案。** 每件的產出是一頁以內。
**不做**:拍截圖、跑完整測試套件、開瀏覽器、全站 grep 填表、寫量測腳本、改 code。
**判斷式**:接到一件事先問「這一步的產出是判斷,還是搜集/執行?」搜集與執行一律改派 Opus;
一張票最多回到 Fable 兩次(開頭、結尾),中途卡住先由 Opus 解。
**唯一例外**:設計稿可由 Fable 全寫,但現況整理仍先由 Opus 交一頁。(#514)
**開票前先跑一次要引用的指令**(2026-09-22):我在 #627 票面寫錯沙盒 server 的旗標與「第二輪會綠」的前提,三條反駁全對。以後票面每一條可執行的東西都先 `--help` 或跑過。
**別在等待時自己動手做 worker 的事**:#620 一行測試修正與 #628/#629 的同步票是例外(設定與量法),產品 code 一律派出去。
