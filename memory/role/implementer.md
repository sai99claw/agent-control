**不做**(84864f3,2026-09-13,實測;#630/#27/#29 補,2026-09-22~23,實測):不 git 寫入(任何動詞);不碰專案 `CLAUDE.md` 列的受保護埠;不讀家目錄秘密;不 kill 不是自己起的行程;不放寬既有斷言;不把期望值改成程式現在印什麼;不寫 `verify/**`(驗證者的,同名檔落地會打架,#630);為回綠給共用夾具加預設值前,反向查它會不會把受測層整個關掉(#27);會執行整支腳本的守衛要有變異關不掉的煞車,且守衛量文件時量**那一段**、不量整份輸出(`--help` 範例行會讓變異存活,#29 M18)。

**`EVIDENCE.md` 必備五段**(82a8b1d,2026-09-21,實測;少任何一段,下一輪的新人會把你查過的路再查一次):① patch sha256;② 閘門指令、`Ran N`、rc;③ 變異表(編號/替換 count/目標斷言/紅訊息首行/還原後 sha256);④ **已排除的假設**:查過什麼、為什麼排除、證據在哪一行;⑤ **最小重現**:一句可以直接貼的指令 + 預期輸出。
**`result` 塊**:見規則包 D-017 段;寫不出來的欄位照實留空,不要編(D-017,2026-09-22,引用;#20 驗收⑦釘句)。
**交付前的回歸**(db32c07,2026-09-21,實測):票閘門的對照表對不到回歸層,綠不等於回歸綠。交付前必跑 `scripts/verify.py --tag <票的 tags 與動到功能的既有標籤>`、**整支瀏覽器模組**(不只對照表挑到的 class);時序類的票再在負載下(`nice -n 19` + 4 支 `yes`,記 PID 只 kill 自己的)把新案例跑 **3 次**;窗口要蓋得住負載下受測那一包的 parse/exec,前提不成立要大聲紅(#642,比照 #639,實測);三組 Ran/OK 貼進 EVIDENCE。一輪把同一層的 bug 全露出來。
**不准輪詢**(db32c07,2026-09-21,實測):測試前景跑、給 timeout、只擷取 `^Ran |^OK|^FAILED|^(FAIL|ERROR):`;不用 Monitor / sleep 迴圈等背景工作 —— 每看一次就是整份上下文重送;丟背景就收回合 = 什麼都沒交,`claude -p` 不會再醒(#26,2026-09-23,實測)。
**紅了誰修**(b65ee79 / 82a8b1d,2026-09-21,實測):閘門紅起**新**實作者(票 + 狀態檔的 `repair_context` + 紅榜),三輪上限;你就是那個新的人時,先讀 `reports/t<票號>/<run_id>/status.json`,**不要重查上一輪已排除的假設**。紅在你沒動到的檔不代表是別人的問題:產品改壞行為本來就會紅在沒修改過的測試檔,歸因未完成前這張票還是你的。
**票寫錯 / 需要裁示 / 案例本身錯**(82a8b1d,2026-09-21,實測):停,寫成票的 `objections[]` 一筆(`category`、`body`、`evidence`、`owner`;阻擋就 `blocking: true`)再報主線 —— 沒被收進票的反駁與沒有反駁長得一樣。案例的 oracle 或 fixture 錯了是 `category: test_defect`:**你不准放寬斷言、不准改 oracle**,主線會派獨立的驗證者修案例。太複雜也提 objection 開票,不准繞路(改名、加第二個欄位、各做各的形狀)(D-018,2026-09-23,引用)。

**測試與 patch 的寫法**(2026-09-22~27,實測):證「兩件事同時在跑」要雙向會合,各寫各的標記、各等對方的,單向標記只擋一種串行(#51);破壞性動作只動自己擁有的狀態,不撤共用夾具(#642);移植舊 patch 到新 base 不信 diff3/patch 自動合併:逐檔套、讀 rej 手解,並以 diff(舊 work, 新 work) 反向核對上游 delta,否則靜默掉行(#13)。
