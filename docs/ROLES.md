# 角色

角色是責任分類,不是七個常駐模型。第一版由少數 session 分時承擔;**作者與審查者要用分離的上下文**。

| 角色 | 誰 | 責任 | 必須交付 | 權限牆 |
|---|---|---|---|---|
| **產品負責人** | 人 | 方向、取捨、必要決策 | 目標、優先序、裁示 | 可暫停、取消、重排;不逐步批准例行工作 |
| **主線** | 跟人互動的 session(預設 Fable 級) | 接需求、開票、維持脈絡、發版、裁示 | 票、裁示、交接、發版紀錄 | 不放寬驗收;不跳過閘門;不替人做產品決策 |
| **排程器** | 輕量 session 或腳本(Sonnet 級即可) | 讀票與寫入範圍,吐「哪幾張可平行、落地順序」 | 一行順序 + 理由 | **只提案**,不執行;不派工、不落地、不寫文件 |
| **落地器** | `scripts/land.sh`(程式) | 套 patch → 閘門 → 合併 → 關票 | 事件與退出碼 | 0 commit 拒絕、基準過期拒絕、越界拒絕、閘門紅拒絕 |
| **Worker** | Opus / Codex sol / 其他 | 在副本裡實作與局部驗證 | patch、測試輸出、變異驗紅、回報 | 只寫自己的副本;禁 git 寫入;範圍擴大要回報不准自己做 |
| **驗證者**(前 Reviewer) | 獨立上下文(Sonnet / Codex sol) | 把票面驗收寫成回歸案例,證明案例對(乾淨主線紅、patch 綠),登記標籤,把怎麼跑寫進票 | `verify/<feature>/test_ticket_<n>.py` + 票的 `verify` 欄 | **不判通過/退回**(閘門判);不讀實作者證據;不重跑閘門;不輪詢 |
| **知識維護** | 主線或指定 session | 更新 code map 與記憶 | 帶來源與版本的變更 | 未驗證推測不進共用知識 |

## 為什麼排程器與落地器要分開
2026-09-10 的實驗:一個 Opus 調度員同時排程、派工、審 patch、落地、寫文件,**一個下午一百萬 token、四十則回報、撞額度後靜停兩天無人發現**。它做對了很多事,但貴的部分全在「超出排序」的那一半。排序便宜,判斷貴;把判斷留給主線,把機械留給程式。

## 模型路由(可調,寫在 `board/config.json`)
| 工作 | 預設 |
|---|---|
| 主線、設計、查 bug 根因、驗收計畫、審稿 | 最高階(Fable 級) |
| 實作 | Opus 級 |
| 排程、機械整理 | Sonnet 級或腳本 |
| 討論、找靈感 | 另一家模型(agy / Codex),**它的回答提到產品功能一律 grep 一次再用** |

額度用完時的政策:**等、換、或送進收件匣;不准默默改走付費通道;協調者自己掛了要有人接手**(`scripts/heartbeat.sh`)。

## 回歸紅了誰去修(2026-09-21,D-G122)
不叫醒舊 worker(它醒來一次 = 累積的整份上下文),也不設常駐調度員。落地器把紅榜寫成 `status.json`,先把紅的案例單獨重跑一次判 flake,真紅就用 headless `claude -p` 起一個**新** worker(票 + 目前 patch + 紅榜 + 上一輪 EVIDENCE),三輪上限。worker 判斷票寫錯 / 需要裁示、或紅在票沒動到的檔 → 停,報主線。理由:2026-09-20 一天 13–14M token,三成花在四輪串行修 bug與驗證者輪詢等閘門。

## 不准輪詢
任何 agent 都不准用 Monitor / sleep 迴圈等背景工作。要跑的測試前景跑、給 timeout、一輪拿結果、只擷取 Ran/OK/FAIL 幾行。
