## 目的與成功指標

agent-control 是一個人控制的多 AI 協作團隊,包含 infra 與每個需求的生命週期控制。它存在的目的,是讓 AI 實作更有效率、token 用得更有效。

成功的定義:我花更少協調時間,就得到更多通過驗收的成果。用四個數字看,都應該隨時間變好:

| 指標 | 往哪個方向是好 |
| --- | --- |
| 每張落地票的 token 與時間 | 下降 |
| 一次就過測試的比例 | 上升 |
| 每張票需要我介入幾次 | 下降 |
| 等我處理的事積了多少 | 下降 |

agent-control 自己的票,以「改善哪一個指標、改善多少」來排優先。加一道關卡、一條規則,就要拿掉一道。

## 一張需求從頭到尾

每個角色做完自己那段就關掉;中間的銜接由腳本做,不靠主線盯。

1. **我跟主線對話。** 主線理解我的需求,轉給開題者。
2. **開題者把需求寫完整。** 寫清楚該做什麼、怎樣算做完。
3. **票跟票之間先排相依性。** 開題者開完票,直接把票放到合適的執行順序上(DAG)。
4. **工作者與驗證者依相依性被派出去。** 工作者實作;驗證者寫測試案例、加進測試系統、確保案例正確,把怎麼跑寫進票裡。做完都把自己關掉。
5. **git 由工作者自己處理。**
6. **工作者做完,觸發 worker-done 腳本。** 工作者只 commit 到自己的分支;腳本確認這張票的驗證案例好了沒。
7. **驗證案例好了,排隊跑測試。** 測試由 agent-control 內建的 regression 系統跑,agent-control 自帶一套 CI。
8. **測試出問題,腳本自動派新工作者修。** 新工作者拿到票、diff、錯誤,直接去解;覺得票本身有問題才問主線。
9. **複雜的票做完後檢查一次。** 只有複雜的票,在整個做完之後檢查結果有沒有符合票的需求。
10. **全綠就落地進主線。** 由腳本合進主線,工作者不直接動主線。

## 看板與統計

整個工作流程要能**不花額外成本**地反映在看板上:看板讀流程本來就會留下的東西,不要求 agent 為了看板多做動作。

- 我可以從看板知道:每張票在哪一步、誰在做、誰被什麼卡住、哪些事等我決定。
- 每個角色使用的 token 數與時間要被統計。每一筆記:角色、票、模型、時間、token(D-045 原話:「角色：票：model:time:token」)。
- 拿不到的數字顯示「未知」,不顯示 0。

## 記憶

角色與模型有多層記憶,能持續進化、變聰明、避免重複犯錯。

- **分層**:角色記憶、模型記憶各自一份;跟專案有關的事記在專案記憶裡,不混進角色或模型記憶。
- **整理**:記憶太長時,由兩個不同的模型或一個更高階的模型討論後整理,不是單一 session 自己刪(D-013)。
- **留什麼**:只留具體的原則、行為準則、思考方式,不直接寫案例;可以引用票號當來源(D-013)。不設固定字數上限:該寫什麼、留多長,由整理的 LLM 決定(2026-10-18,推翻 D-006)。

## 明確不是我要的

下面三類不是我要的(2026-10-18 確認)。現有的實作要列進減法清單,每一項附上「拿掉會怎樣」交我裁。

1. **驗證層層疊加**:每張票都派 reviewer、閘門機械格、案例 lint F1–F12、寫測試前答四問、#106 開題要實跑證據、#98 覆核綁內容、#104 反駁逐條處置。我要的是:工作者自己的單元測試 + 驗證者的案例 + 測試跑過,複雜的票再加一次做完後的需求檢查。
2. **寫入範圍那一整套**:allowed\_write\_paths、in\_scope、out\_of\_scope、protected\_paths、hint\_scope、info\_homes。
3. **同一件事存好幾份**:events.jsonl、票 JSON、status.json、收件匣 index、reports、metrics。看板要的是一份狀態,不是好幾份互相對帳。
