## 1. 在自己的 worktree / 分支 commit

**worker**(D-054 Q9,VISION 流程 #5「git 由工作者自己處理」):派工方(`auto-fix.sh`)派工前建好
票分支(`t<n>`,票的 `branch` 欄)的 git worktree `<worktree_dir>/<票分支>`,你的 cwd 就是它;
閘門在同一個 worktree 跑,落地收的也是這條分支(流程見 `docs/WORKFLOW.md`)。
派工方兩種形式都是 `auto-fix.sh`(D-061):它自己起 headless worker,或 `--prepare worker|verifier` 備好後由主線交給
in-session subagent(subagent 的 cwd 每次呼叫重設,指令一律帶 worktree / 副本路徑)。底下 rc 8 的越界守衛只包得到
auto-fix 自己起的程序;in-session 的規矩一字不差。

- **在自己的 worktree / 分支 commit**:改完 `git add` / `git commit`(可多個 commit,訊息帶 `t<n>`)。
- **交件 = 分支相對派工前多了至少一個 commit,而且工作樹乾淨。** 沒 commit 的改動不算交件,
  腳本不替你 commit;commit 了又留著未 commit 的改動,當作沒交。
- EVIDENCE 寫在 worktree 外的輪次目錄(派工文給絕對路徑),不進 repo。
- **不碰 main、不 push、不 merge / rebase 進 main、不動別的分支、不 worktree add / remove**。
  主 repo 的 HEAD / 分支、`refs/heads` 底下別的分支、`hard_block.dirs` 動了 → `auto-fix.sh` 的越界守衛 rc 8。
  **為什麼**:進主線只由 `land.sh` 在測試綠後做 —— 落地要決定分支順序、在 land 佇列裡排、處理與
  別張票的衝突,而你看不到別張票。

**驗證者**仍在 `git archive` 展的副本(`work/` 改、`base/` 是對照組)交 `patch-verify.diff`,不 git 寫入
(規矩在它的角色卡與 `templates/dispatch-verifier.md`);收件時 `apply.sh` 在票分支上替它補一個 commit。

🩸 **base 要對**:派工方 `git archive <ref>` 前先 `git log --oneline -1 <ref>` 對一眼標題 ——
archive 給的是 commit 的內容,worktree 裡沒 commit 的一個字都不進去,**而且一聲不吭**
(2026-09-10:漏了 commit 的 branch 做出一份看起來正常、其實少一張票的樹)。印出的 sha 就是
派工文「base = `<sha>`」與票的 `base_sha`(`tickets/SCHEMA.md`),三處出自同一次 `git log`。

**只准跑的測試(唯一正文;worker 與驗證者同一條)**:只跑派工文「## 只准跑的測試」段列的測試
(#87 A18;那一段由 `auto-fix.sh` 逐字抄票的 `test_plan`)。不跑全套(unittest discover 整組、
`gate.sh --full`)、不跑 `verify.py` 全部回歸 —— 回歸是閘門的事,閘門紅由 auto-fix 下一輪派 worker
處理,全套只在 land 跑一次。票沒有 `test_plan` 時那一段寫「只跑你改到的 tests/ 檔」,照它做。
負載下重跑、逐模組分批跑,**只在票的 `test_plan` 明列時才做**(#70、#642)。

## 2. 禁區

- **埠**:`<受保護的埠>`(prod / staging / 看板 / portal)。自己起的測試 server 用 OS
  自動配的埠(`("127.0.0.1", 0)`)。
- **目錄**:`<資料與秘密目錄>`。
- **指令**:`<副本裡不准跑的腳本>`(部署、建置、發版、容器、服務管理)。發版是主線的事。

這三格由專案填(`templates/project-CLAUDE.md`)。**空著的派工文不要發** —— 一份沒有
禁區的派工文,跟一份禁區剛好是空的派工文長得一樣。

**沒有寫入範圍;機器會擋的只有一份清單**:`board/config.json` 的 `hard_block`(D-054 Q2、Q3)。`paths`(repo 內 glob:
裁示文件、發版腳本)動到 → `apply.sh` rc 5(量票分支上的 commit 加 patch-verify)、`gate.sh` preflight rc 4、`land.sh` 拒收;`dirs`(repo 外
目錄,`~` 展開、相對主 repo 解析)底下的檔被 agent 動到 → `auto-fix.sh` 的越界守衛 rc 8;`patterns`
(改動內文禁字 regex)**只查 tests/** 與 verify/** 的新增行**,命中同 `paths` 三處擋 —— scripts 自己合法用
kill,不查。沒設或三格皆空 = 不擋。

🩸 **不准殺任何不是自己起的行程**;不准 `pkill -f`、不准 `killall`、不准照 `ps` 的輸出猜
「這看起來像我的」。這台機器上同時有好幾條線在跑,殺錯一發是別人幾十分鐘的工作
(2026-09-10:用 PID 殺掉另一條線正在跑的回歸)。測試卡住就用 `timeout` 包起來重跑,不獵行程。

## 3. 判綠只能看測試自己說的話

🩸 **`cmd | tail`、`cmd | grep`、`cmd | head` 的退出碼都是右邊那一支的。**
實測:`sh -c 'false | tail -1'` 退出碼是 **0**。所以「跑完 `| tail -6` 看一眼」在三種情況會靜靜
判綠,三種都發生過:測試根本沒跑起來(import 炸、沒裝依賴、指令打錯);`Ran … / OK / FAILED`
不在 `tail -N` 的視窗裡(瀏覽器那幾支在摘要後面再印一大段);管線中途斷掉(`SIGPIPE`)。

**正確形狀**(`<指令>` 是派工文「只准跑的測試」段給你的那一句):

```sh
<指令> > run.log 2>&1; rc=$?
grep -aE "^Ran |^OK|^FAILED" run.log      # 給人看的
[ "$rc" -eq 0 ] || { echo "紅了,看 run.log"; exit 1; }
```

背景跑的一樣中招。驗證者的 `git archive` 副本不是 git 樹,閘門的分支形式在那裡是空閘門 —— 不要在副本裡拿它量綠。

**不准輪詢**(短命角色的唯一正文;主線的在 `CLAUDE.md`「不可違反的」):測試與指令一律**前景跑、
加 `timeout`**,不用 Monitor、`sleep` 迴圈或反覆看狀態去等背景工作 —— 每看一次就是整份上下文重送一輪
(2026-09-21:重跑整組 + 輪詢等它,一天燒掉幾十萬 token)。🩸 headless session 把工作丟到背景就結束回合,
等於什麼都沒交,不會再醒(#26)。等不到的東西寫進回報,不要等。

## 4. 不准收窄執行環境(瀏覽器引擎、平台、資料庫版本)

**不要設「只跑某一個引擎」那種環境變數。** 不設它拿到的就是這台機器此刻真的驅動得動
的每一個;測試框架的 `available()` 會把跑不動的標成「量不了」**並印出原因**。

🩸 一支「只記不改」的 `fetch` 包裝寫成 `real.apply(this, a)`,Firefox 對 `this` 認真、Chrome 不管;
分支閘門收窄成 chrome 全綠,一路藏到 land 的全套才爆(2026-09-10;修法 `window.fetch.bind(window)`)。

只有**完全不碰那一側**的票才可以為了速度收窄。

## 5. 變異驗紅:沒驗紅的測試等於沒有測試

**變異表選填**(D-054 Q10):有做變異就寫,沒做不算缺段。每一條寫成「改什麼 → 哪條斷言紅 → 失敗訊息片段」,做完還原(還原後對 sha256)。

🩸 **變異之後,先確認被改的那一行真的變了,再看測試紅不紅**(diff 一下,或把那一行印出來)。
**「變異沒生效」與「守衛有漏洞」長得一模一樣** —— 那正是整類假綠的母題(2026-09-10:
`str.replace` 打到錯位置,測試照綠;那位 agent 自己發現並寫明「是我的腳本錯,不是守衛漏」,
**這一筆比它修的 bug 更值錢**,照這樣誠實記)。

**不准為了讓測試綠而放寬既有斷言**(把逐字比對改成 `assertIn` 之類)。真的需要放寬,
單獨提出來讓人裁(§7)。

🩸 三種「變異沒殺掉,而測試看起來是對的」(2026-09-10):
- 量錯對象:`overflow: hidden` 的容器照樣寫得進 `scrollTop`,「捲到底驗尾端可達」對裁掉的頁面是綠的;
  要量的是 `overflowY` 本身。
- 判準選到「壞掉時碰巧為真」的那一個(用「訊息區有字了沒」證明某件事,而那句話壞掉時會先成立);
  判準要選壞掉時**必然為假**的。
- 鎖吃掉證據:一個 inflight 鎖讓壞的版本與對的版本送出的請求數逐字相同。

## 5.5 🩸 常設條款:「沒有東西可做」與「做完了」長得一樣

> **`[]` 是「看著,而一發都沒有」,`None` 是「這台根本沒在看」。**

那兩件事揉成同一個空 list 的那一刻,「一發請求都沒有」那種斷言就永遠是綠的,而且
**與真的驗過長得一模一樣**。這是假綠的母題,而且它會持續生產 —— 2026-09-10 一天遇到的實例裡
**三個是當天新做的東西自己帶來的**,所以這是常設條款,不是歷史紀錄。

**判準,寫任何一個檢查之前先問**:

> **它答不出來的時候,長什麼樣?**

如果答案是「**跟通過一樣**」,那個檢查還沒寫完。常見的「答不出來」偽裝成「通過」:
- **拿不到就當空的**:`getattr(x, "attr", [])`、`.get(k, "")`、`or []` —— 空集合對「有沒有東西」的斷言是通過。
  讓它拒答,不要回空。
- **能力不足被當成答案**:某個引擎 / 環境模擬不了,程式回預設值而不是「我不知道」。**明列並印出原因**。
- **沒有輸入也算跑過**:0 個 commit、0 條測試、0 個檔案 —— 迴圈跑了零次是成功的。開跑前印出要處理的
  東西,0 就拒絕。
- **在受控環境裡成立**:演練、沙盒、`--dry-run` 把代價拿掉,有時正好拿掉「這條路真的會被走到嗎」
  (十條演練全綠,那一輪落地跑的還是舊腳本)。新行為第一次真跑是在下一輪,那一輪才驗得到(§5.55)。
- **沒有人看得出來的壞**:兩處 `color:` 從來沒生效過而畫面一直正常;抓到它的是換色時順手量對比。
  「沒有人回報」不是證據 —— 使用者回報得了的是**他知道該長什麼樣**的東西。
- **外部模型的具體與正確長得一樣**:它不會在猜的那一格寫得比較模糊。凡提到產品功能、欄位、畫面元素,
  一律對著 repo `grep` 一次再用。
- **驗證工具自己的輸入錯了**:關票前 grep 一個原始碼裡根本不長那樣的字串,`0` 跟「東西沒進主線」的 0
  一模一樣。驗之前先看那個字串在原始碼裡到底長什麼樣,挑只有這張票才有、以字面存在的。
- **管線的退出碼**(§3)、**變異沒生效**(§5)、**`if __name__` 擺在檔案中間**(直接跑與 `-m unittest`
  的測試數不同)—— 同一家族。

### 過期的綠與有效的綠也長得一樣

**「閘門綠」是對某一個 base 說的。** 分支擱著沒落地的期間主線往前走,那個綠就從「這份改動是好的」
變成「這份改動在某一天對著那時的主線是好的」—— 而畫面上那一行 `OK` 一個字都沒變。
**固定動作**:記下每次閘門跑在哪個 commit(那就是票的 `base_sha`);落地或解凍前先比對主線現在在哪,
不同就重跑,不拿舊的 `OK` 送(`land.sh` 現在會替你問:`base_sha` 不是主線祖先就拒絕)。

## 5.55 🩸 常設條款:新工具的第一次真跑,要有人在場確認

演練綠只證明「在受控環境裡這樣寫是對的」;新行為第一次真的被觸發,才是它第一次在真的路徑上成立,
而那兩件事在畫面上長得一樣(§5.5)。**規矩**:發出新守衛或工具的人,排一次真跑的確認並寫下**要看到
什麼**;下一次它第一次真的被觸發時,誰在場誰確認一眼。清單住 `docs/REHEARSAL.md`(控制台第 ⑤ 段畫它);
**它不是待辦**,是「哪些保證還只在演練裡成立」的清單,確認過就刪那一列。

## 5.6 🩸 演練環境要真,不要造一個自己寫的模擬器

> **「假一支出來,等於在測我自己寫的模擬器。」**(2026-09-10,一位實作者拒絕替 `land.sh` 造假 git)

**判準**:替演練造替身之前先問 —— **這一段程式碼的正確性,是不是就寄託在被我替換掉的那個東西的
語意上?** 是就不能替換,用真的(tempdir 裡的拋棄式真 repo)。**該替換的是「代價」而不是「語意」**:
全套閘門換成一支寫標記檔就退出的腳本可以 —— 它省掉九分鐘,還把「全套到底有沒有被叫到」變成看得見的
事實;git 本身換成假 git 不可以 —— 測到的會是模擬器對 git 的理解。

## 5.7 🩸 守衛的產出是一個**可執行的動作**,不是一句「有問題」

> **一個守衛給錯了下一步,跟沒有守衛不一樣 —— 它更糟。** 因為那個人會照著做,然後以為處理完了。

範例是 2026-09-10 的憑證守衛:`git ls-files --cached` **同時裝著「剛 add 的」與「三個月前就 commit 了的」**,
對後者說「`git rm --cached` 還救得回來」是假話。所以它問三次,**每一格給不同的下一步**:

| 格 | 怎麼問 | 訊息說的下一步 |
|---|---|---|
| 工作樹 | `git ls-files -z --others --exclude-standard` | 下一個 `git add -A` 會把它掃進去 |
| 索引 | `--cached` **且不在 HEAD** | `git rm --cached` **現在**還救得回來 |
| 歷史 | 在 `git ls-tree -r -z HEAD` 裡 | **清不掉,停下來報上去,不要自己刪** |

**變異驗紅要驗到「下一步是對的」**,不只是「有紅」:拿掉 HEAD 那一問守衛照樣紅,但訊息變成假話 ——
只斷言「rc != 0」的變異是綠的。

**抓與放的代價不對稱:內容只用來脫罪,不用來抓。** 掃內容抓人會教會人繞過去(把 key 拆兩段接起來),
繞過去的那一份看起來跟乾淨的一模一樣;檔名這條線繞不過去。抓錯了是吵一次,放過了是靜的 ——
脫罪那一段故意寫得笨,寧可多紅一次。**不加白名單**:誤判的處置是改檔名,不是在守衛裡加例外 ——
白名單只是把這次的判斷藏起來,它靜默失效的那天沒有人會知道。

**`-z` 不是效能參數,是正確性參數**:`git ls-files` / `ls-tree` 不加 `-z`,非 ASCII 路徑會被逃逸印出,
而逃逸過的字串 `open()` 開不起來 —— 安靜地變成「掃不到」。任何「列出檔案再逐一開啟」的程式碼都吃這一條。

**失敗訊息不把秘密抄進第二個地方**:守衛的訊息會落進 log、CI 輸出與回報;只說第幾行、多長、哪一種形狀。

## 6. 查證

**查實作位置先問 repo map**:`python3 scripts/repo-map.py query <主題>`(入口、主守衛、來源、文件);
查不到(rc 1)或 `repo-map.py check` 非零(索引過期)才對來源針對性 grep。子命令與索引歸誰見 `docs/CODE-MAP.md` §0。

### 6.3 🩸 要數某條規則會抓到多少東西,就用**那條規則本身**去數

近似的搜尋條件數出來的是**假的下界**,而它看起來是一個精確的數字 —— 讀的人不會知道要打折。
2026-09-10 一天三次低估、三次都寫成確數(用眼睛數 class 漏 34 條測試;抽樣看幾支漏 246 處;
用比守衛窄的關鍵字數出「三處」實際七處)。

**規矩**:先把判準寫出來(哪怕只是一行 `grep -E`),再用它數;做不到就把數字寫成**下界並說明條件**
(「至少 N,用 X 條件數的,與守衛判準不同」)。寫票的人是在**還沒有守衛**時盤點的,實作者是裝上守衛後才看到
真實範圍 —— 兩邊數字不一致是常態;票面標成下界,實作者就不必猜是誰錯。

### 6.4 🩸 回報裡要標記:這是**讀出來的**還是**實測的**

**「讀 code 得出的結論」與「實測得出的結論」在回報裡長得一樣** —— 兩者都是一句肯定句,兩者都可能對。
差別在**它錯的時候誰會發現**:實測錯了,重跑一次就露餡;讀錯了,它會被下游當成事實用下去,
**而下游沒有辦法分辨**。

**規矩**:凡是寫進回報或票面的事實性斷言,**標記來源** —— 「(讀 code 推的,未實測)」或
「(實測:指令 X,輸出 Y)」。2026-09-10 兩次:讀 CSS 推焦點框對比不足,實測 5.70;票面寫「實測 12.2 秒」,
真量是 4.01 / 49.00 / 4.02,那個數字一路傳到派工文。

**推翻上游指示的時候這條特別重要**:推翻需要的證據等級比照做高,而「我讀了 code」不是那個等級。

## 6.5 發現問題與處置問題要分開

**掃到一個沒人料到的東西時,回報它,不要順手處理它。** 派工文裡的固定句(照抄):
> 如果你掃到 repo 裡**現在就有**長得像憑證的檔,**先停下來講**,不要自己刪。

為什麼是規矩不是客套:**處置需要的上下文發現者多半沒有**(那個檔可能別人正在用、刻意留的、刪了會讓
另一條線紅);**處置會把證據蓋掉**(下一個人看到的是乾淨的 repo,不是「這裡差點 commit 一個憑證」);
**發現本身就是交付**(「我掃到這三個,沒動」可以被覆核,「我清乾淨了」只能被相信)。
同一條也適用於第三份重複程式碼、別的呼叫端犯同一個錯、與票面無關的既有 bug:列出未動。

## 7. 「票寫錯就說出來」

派工文最後一段固定要求:**發現票或驗收計畫哪裡與現在的程式對不上、或哪一條要求做不到 / 做了會壞
別的東西,直接說出來,不要硬做。** 怎麼說、說了之後誰接手,見 §8 第 7 點。

📏 這一條回收率很高:2026-09-10 三張票分別查出「圖示本來就對,問題在別的表面」、票面那句是照一行
讀了不存在節點的失敗訊息寫的、驗收計畫用詞錯了 —— 三次都是實作者對。

### 7.1 驗收寫的是使用者看到的結果,不是實作細節(D-H38,#61)

開題那一側的規矩在 `memory/role/opener.md` 與 `tickets/SCHEMA.md` acceptance 那一格;這裡寫接手的人怎麼讀:
- **驗收條目驗的是使用者看到的結果**。DOM 結構、樣式掛在哪個元素、金額帶不帶幣別,票面沒說要改的一律
  **照產品既有慣例** —— 驗證者照慣例斷言,實作者照慣例寫;票面字面與慣例衝突時照慣例做、EVIDENCE 記一行
  `OBJECTION: ticket-wrong`,不要兩份各寫一份。
- **釘著舊行為的測試 / 期望檔 / lib 腳本跟著改,不是越界**:票沒有寫入範圍(D-054 Q2),會跟著動的照改;
  唯一的硬擋是 `hard_block`(§2)。
- **票面寫「其餘斷言不變」卻沒列查過哪幾個檔**,那一句是沒驗過的假設:撞到既有 oracle 就照 §7 說出來,
  不准把舊斷言放寬成新行為印的東西。

## 8. 回報格式(派工文要明列)

1. 交件在哪:worker 寫票分支名與分支頭 sha + `git diff --stat <base_sha>..HEAD`;驗證者寫 `patch-verify.diff`
   **相對副本根的路徑** + diffstat。不寫家目錄絕對路徑 ——
   回報與反駁行都會被抄進票與看板(`test_no_project_names` 會擋)。
2. 做了什麼 —— **寫給不看 code 的人也讀得懂**(那份摘要會被轉給使用者)。
3. 測試輸出**逐字**(含 `rc=` 與 `Ran … / OK`),skip 的原因**逐字**貼上來。
4. 變異驗紅表:**選填**,有變異就寫、沒有不缺段(D-054 Q10;worker 限定,驗證者不做變異,D-020)。
5. **已排除的假設**:查過什麼、為什麼排除、證據在哪一行。
6. **最小重現**:一句可以直接貼的指令 + 預期輸出。
   5 與 6 是給**下一輪那個新的人**的:少了它們,三輪可能把同一段 code 查三次 —— 每一次都是整份上下文
   重付一遍。**有長度上限,不搬整段聊天。**
7. 票寫錯、發現的別的問題、**案例本身錯**(oracle 或 fixture):在 EVIDENCE 寫一行
   `OBJECTION: <ticket-wrong|test_defect|blocking> <一句話>`,收件的那一手(`apply.sh` / `auto-fix.sh`)
   把它記成票的 `objections[]` 一筆(`category` / `body` / `evidence` / `owner`),不要只寫在回報裡 ——
   **沒被收進票的反駁,與沒有反駁長得一樣**。`ticket-wrong` / `blocking` 由 auto-fix 起開題者判;
   開題者一輪只有兩種結果:判 accepted(票面改好,含把你讀錯的地方澄清進票面)會把你接回同一個 session 在原處續做
   (worker 的 worktree、驗證者的副本;續做的規矩在實作者角色卡);判 escalate 就帶一題附建議的裁示題轉主線。只有四種情況
   才進主線收件匣 —— 流程正文在 `docs/WORKFLOW.md`「實作者的反駁怎麼被收下」。
   案例錯是 `category: test_defect`:**你不准放寬斷言、不准改 oracle**,auto-fix 會派獨立的驗證者修案例。
   反駁行裡的家目錄路徑收件時會換成佔位(#91 C4),仍不要寫。
8. **記憶**:有寫就列 `memory.py note` 的那幾行(層 / 名 / 那一句 / 票號),沒寫就寫「無」。
   **沒列的回寫,與亂寫長得一樣** —— 主線靠這一段 grep 誰動了哪一層。

改到使用者看得到的文字時,**把「舊 → 新」的完整對照表列出來** —— 那是使用者會逐句看的東西。

## 8.5 🩸 結構化交付:EVIDENCE 尾端那一塊 `result`

§8 是寫給人看的;同一份檔的**最後**再加一段 `## result` 與一塊語言標記是 `result` 的 fenced JSON(寫給機器看的)——
鍵、型別、抽取、缺漏的三種樣子與範例只有一份正文,照 `tickets/SCHEMA.md`「EVIDENCE 尾端的 `result` 區塊」寫(D-054 Q12)。
