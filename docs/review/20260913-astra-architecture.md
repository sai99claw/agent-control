整體方向合理，但目前是**有局部守衛的協作工具箱，尚未形成能強制執行規範的控制系統**。七個核心想法可以保留；優先補齊狀態、身分、證據與寫入的一致性，不宜先擴充更多角色或看板功能。

本次僅讀指定材料，未改檔、未跑 git、未連網。以下行為判斷均為**讀程式推論，未實測**；既有測試只讀未執行。環境禁止寫檔，故 **`./REVIEW.md` 未建立**，完整審稿貼於下方。

例如 `state_version` 每次加一只是**計數器**；沒有要求呼叫者帶預期版本、並在同一交易比較，就不能防止遲到或並行覆寫。

**3. 票應搬出 Git，採單一持久 runtime 儲存**

建議單機第一版使用 **repo 外的 SQLite**，按 `project_id` 隔離。票、attempt、session、租約、事件與使用者回答放在同一交易邊界；裁示與長期知識保留在 code repo。

理由不只是少排一次落地鎖：

- `ticket.py:111` 以最大 ID＋1 取號，兩個開題者可能取得同號。
- `ticket.py:96` 的暫存檔＋rename 避免半份 JSON，**不避免最後寫入者蓋掉前者**。
- 票先保存、事件後發送，兩步間中斷就會分岔。
- 各 worktree 若各自使用相對 `tickets/`，可能讀到不同版本的控制狀態。
- STATE 樣本已記錄一上午三次撞號；切號段只是人工補救。

SQLite 交易應同時完成「驗預期版本 → 改票 → 加事件」；Git 落地另以穩定 operation ID 記錄階段，重啟後對照實際 ref 恢復，因為資料庫與 Git 無法靠單一交易一起提交。

短期若保留 JSON，也應搬出 repo，使用**獨立、短時間的票庫鎖**保護取號和讀改寫；不要讓開票等待九分鐘全套測試。

另外，不能只改 `tickets_dir`：`event.py` 支援絕對路徑，但 `land.sh:95` 直接組成 `$ROOT/$TICKETS/$id.json`，兩邊解析並不一致。

**4. 模型記憶存在多個假保證**

2K **字元軟門檻**本身合理，不等於 2K token；超限不停工也是明示政策，不應算漏洞。真正的問題是：

- **提高上限不必附理由。** `memory.py:225` 讀出檔內 `cap_chars` 後直接比較，不驗 `cap_history` 或 discussion；`test_memory.py:61` 還要求「2600 上限＋空 history」通過。
- **空白範本也算討論完成。** `memory.py:325` 只找 `## 結論` 子字串；原始 `templates/discussion.md` 就含此標題。
- **直接刪短記憶可繞過 consolidate。** `check` 不比較前後版本，無法知道來源、反例或分歧被刪掉。
- **2K 不限制實際必讀上下文。** front matter 不計數、inbox 不限量；開場只是要求讀整份檔，沒有產生受控的正文閱讀包。
- **整理不是原子操作。** `memory.py:353` 先刪 inbox，再寫主檔；中間失敗可能遺失筆記，並行寫入也沒有鎖。
- **整理完成事件發得太早。** 先發 `memory.consolidated`，之後才判斷仍超限並回傳 1。
- 自動整理票只允許寫記憶與 inbox，卻要求新增 `discussions/...`；照範圍交付會撞上自己的落地越界守衛。

建議將老師帶學生保留為審查方法，程式只承諾能證明的部分：雙方身分、非空結論、來源與分歧欄位、記憶前後雜湊、上限核准紀錄及原子套用。**格式驗證不能證明真的思考或學會了。**

**5. 看板只反映部分回報，不能代表 agent 實況**

已自動接上的：票 CLI 變更、land 的部分階段、記憶操作、網頁回答。仍靠 agent 主動發送的：派工、attempt 開始／結束、排程、session 結束、發版；直接執行 `gate.sh` 本身也不發 gate 事件。

具體盲點：

| 看不到或可能誤判的事 | 原因 |
|---|---|
| session 正常結束 | `event.py:123` 記 CLI 子程序 PID；`board.py:126` 用 PID 配對，不是穩定 session ID |
| worker 已死、失聯或被取消 | 無 end 就顯示「在跑」；看板未接 heartbeat 逾時結果 |
| worker 和 reviewer 同票同 attempt | 時間線只以 `(ticket, attempt)` 當鍵，角色可能互相覆蓋 |
| 誰持鎖、等誰、瀏覽器資源被誰占用 | 沒有鎖／資源投影 |
| review、patch、測試報告是否同一版 | 沒有完整證據鏈 |
| main 已前進而舊測試證據失效 | 只查 base 是否仍是祖先 |
| 排程理由、局部 gate、記憶及 release 事件 | 一般事件沒有完整呈現在頁面；`/api/state` 還移除原始 events |
| code-map 過期 | 文件承諾顯示，board 未讀取 |
| 回答已存但尚未形成裁示 | 網頁只列 `NeedsDecision`；CLI 的判準則只是 DECISIONS 出現票號 |

最後一項還有版本漏洞：同票已被裁示引用後，使用者再次改答案，`decided_tickets()` 仍視為已處理，未辨識**新的答案版本**。

STATE 樣本中「跑中的 agent 其實隨前任結束」正是目前看板無法解決的問題。應呈現「最後觀測、已失聯、待確認」，而不是把缺少 end 當存活證據。

**6. 「clone 後就能開始用」目前只成立於工具展示**

README 記錄的演練是 new-session、建票、事件、看板、heartbeat、verify，沒有證明「需求 → 開題 → 派工 → patch → 獨立覆核 → 落地 → 關票 → 重啟接手」閉環。

新專案至少缺：

1. **接入與路徑契約**：工具來源、專案根、runtime 根、主分支、worktree、報告與備份位置。Python 的 `AC_ROOT` 與 shell 自行推根目錄並不一致。
2. **真正的專案閘門**：安裝依賴、測試對照、必要套件及 skip 政策；現有 gate 測的是 agent-control 自己。
3. **能力與權限設定**：模型工具能否啟動、查狀態、停止、取得用量；worker 隔離要由環境執行，無 `.git` 不等於不能碰 repo 外路徑。
4. **可用的角色入口**：opener、dispatcher、worker、reviewer 的上下文包與回報契約；未填禁區占位符要阻止派工。
5. **持久交接及恢复流程**：agent ID、attempt、交件雜湊、剩餘工作、鎖與遠端／本機落地階段。
6. **新專案端到端驗收**：包含覆核退回重做、逾時接手、並行開票與中斷恢復。

建議把目前承諾改為「clone 可啟動工具與示範看板；接入專案需完成初始化檢查」。

**7. 最容易假綠的三個地方**

1. **Done 沒有完成關卡。** `ticket.py set <id> state Done` 不走 verify；create 也接受 Done。即使使用 close，弱檢查仍可因別張票改過同範圍而成功，且不要求 review 或測試證據。
2. **祖先檢查冒充證據有效性。** `base_sha` 在 main 正常前進後仍是祖先；`test_land.py` 的 stale 案例測的是旁支 commit，沒有測真正「舊綠」。land 會重跑候選全套，這一層有價值，但不能使舊 review／局部測試自動有效。
3. **整理格式冒充討論與核准。** 空結論標題可通過，直接提高 `cap_chars` 可變綠；現有測試未阻止，部分還固定了這種行為。

**P1：必改**

- **P1-1｜main 寫入未互斥，目標也未充分確認。** `land.sh` 沒有共用鎖；第 208 行 merge 到 `$ROOT` 的目前 checkout，未確認就是設定的主分支。應統一 land／docs／其他 main 寫入入口，驗證工作樹、固定候選 SHA 並做預期 ref 比對。
- **P1-2｜完成與覆核關卡可繞過。** 收緊所有狀態入口；禁止任意設 Done，強制依賴、凍結、attempt、review 與候選證據檢查。`land.sh` 現在既不檢查 review，也不自動關票。
- **P1-3｜票庫並行寫入會丟資料或撞號。** 原子取號、比較版本更新、票與事件交易化；runtime 與 code 歷史分開。
- **P1-4｜session／attempt 身分及接管不可靠。** 穩定 ID、存活觀測、過期回報拒收、接管前查證，並接上五票輪替；用量未知時不能宣稱已執行 20 萬 token 限制。
- **P1-5｜記憶整理的核准可繞過，且有遺失筆記窗口。** 修正上限驗證、討論紀錄與原子套用；所有記憶寫入路徑都受同一規則檢查。
